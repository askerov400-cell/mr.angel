# Автоматическая память в переписке

Статус: реализация развёрнута; ожидается проверка автоматической памяти пользователем в Telegram.

## Цель

Во время обычного общения Хранитель определяет полезную информацию, сохраняет её и использует при ответе.

## Требования

- Цепочка: сообщение Telegram → классификатор → проверка результата → запись в Supabase → загрузка памяти → ответ.
- FACT, GOAL, EVENT и OBSERVATION сохраняются отдельно. IGNORE не записывается. STATE хранит текущее значение и историю изменений.
- Каждая операция получает ID пользователя из Telegram. Общие JSON-файлы без принадлежности пользователю не подключать к переписке.
- Одинаковые записи одного пользователя не дублируются. Записи разных пользователей не смешиваются.
- Недостоверный ответ классификатора не приводит к записи. OBSERVATION передаётся модели как предположение, а не факт.
- Ошибка классификации или сохранения не прерывает общение; в ответе нельзя утверждать, что память сохранена, если запись не подтверждена.
- `/remember`, `/memory` и `/clear` сохраняют назначение. `/clear` очищает диалог, а не долговременную память.
- Логи показывают этапы и результат без текстов переписки и секретов.
- Существующие SQLite- и JSON-данные сохраняются; импорт не смешивает записи без установленного владельца.
- Только бесплатный тариф Supabase. Платные ресурсы не создавать.
- Автоматическая память работает только в личном чате. В группах личная память не сохраняется и не раскрывается.
- Для автоматических FACT, GOAL, EVENT и OBSERVATION используется отдельная таблица `memory_entries`; ручные факты остаются в `facts`. Состояния — `user_states`, история — `state_history`.
- Точная дедупликация автоматических записей выполняется в БД по пользователю, типу и нормализованному тексту. Смысловая дедупликация перефразировок в этот этап не входит.
- Классификатор обрабатывает одну запись из сообщения; извлечение нескольких отдельных фактов — последующий этап.
- Запись допускается при корректном типе и уверенности не ниже 0.8; ошибочный или неполный ответ пропускается.
- Изменение состояния и запись предыдущего значения выполняются одной транзакцией. Неизменившееся состояние не добавляет историю.
- Ошибки памяти не блокируют ответ; результат записи явно передаётся отвечающей модели. Загрузка контекста ограничена последними записями.

## Критерии готовности

- Проверены все типы памяти и отказ классификатора.
- Два пользователя не видят память друг друга.
- Повторный факт не создаёт дубль; изменение состояния сохраняет историю.
- Проверены запись и чтение из Supabase и недоступность данных публичным ролям.
- Через Telegram проверены факт, состояние и обычное приветствие.

## Текущее ограничение

Существующие JSON-записи не имеют подтверждённого владельца и не импортируются автоматически. Старые экспериментальные модули остаются вне рабочей цепочки Telegram.

## Проверки реализации

- 16 локальных тестов пройдены: валидация типов, отказ классификатора и записи, сохранение владельца, безопасные ошибки, маркировка предположений и интеграция Telegram-обработчика. Личная история и память не передаются в групповые ответы.
- SQL-проверки с откатом прошли: точный дубль, неизменившееся состояние и история прежнего значения.
- Реальное REST API через ключ приложения проверено на синтетическом владельце: запись, повтор, чтение, обновление состояния и фильтр другого пользователя.
- Реальный классификатор: приветствие пропущено, устойчивый факт распознан как FACT.
- Синтетические данные удалены после проверки.
- Проверка безопасности: только INFO об отсутствии публичных политик, ожидаемое поведение закрытой серверной памяти.
- Railway развернул коммит `7058dbd`: SUCCESS; Supabase и Telegram подтверждены логами, ошибок и Conflict при проверке нет. Источник Railway переведён на ветку main без привязки к старому коммиту.
- Автоматическая цепочка обработчика проверена с подменой Telegram и модели; реальная проверка автоматического сохранения через Telegram ещё предстоит. Отправка сообщений от имени пользователя не выполнялась.
